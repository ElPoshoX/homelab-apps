# OneUptime incident notifications to Discord

## Runtime identity

The OneUptime chart is pinned to chart and image version `10.5.29`. Its default `release` image tag moved independently of the chart and caused a new nginx pod to fail. The pinned image and a 10-second nginx startup probe restored a healthy rollout.

Kustomize Helm rendering does not preserve the chart's generated `oneuptime-secrets` values. The SOPS-managed `oneuptime-runtime-secret` preserves the `ONEUPTIME_SECRET`, `ENCRYPTION_SECRET`, `REGISTER_PROBE_KEY`, and `PROBE_KEY` values used by the running pods. The app and worker use the chart's `externalSecrets` references; the probe uses a Kustomize patch to reference the same stable Secret. The generated Secret is removed from the rendered manifests. A probe restart after this change retained its existing probe ID and monitor assignment.

## Discord delivery

The Discord webhook is stored in the SOPS-managed `oneuptime-discord-secret`. The OneUptime database also has a global workflow variable named `DISCORD_WEBHOOK_URL` with `isSecret=true`; this hides the value in workflow logs. The workflows are configured in OneUptime's PostgreSQL database, not generated by GitOps.

- `Incidents to Discord` runs on `incident-on-create`. It selects the incident title and description, then posts a red Discord embed through the API Post component.
- `Resolved incidents to Discord` runs on `incident-state-timeline-on-create`. It only follows the `yes` branch when the newly created timeline row has the Resolved state ID. It looks up the incident title and posts a green embed. Triggering on the timeline row prevents repeated messages from unrelated updates to an already resolved incident.
- Both embeds link to the OneUptime incident dashboard, show status and environment, and suppress Discord mentions. The API Post URL adds `?wait=true` so a successful run records Discord's HTTP 200 response and message ID.

The previous enabled Telegram test workflow was replaced with the Discord creation workflow.

## Verification

On 2026-11-26 UTC, a controlled outage of the Speedtest monitor created one incident and one Discord opening message. Restoring the original monitor destination and 30-minute interval returned the monitor to Operational, automatically resolved the incident, and produced one Discord recovery message. Both workflow runs returned HTTP 200 and Discord message IDs. The opening card described the Speedtest failure once; the recovery card described the restored service. The webhook value was absent from the inspected workflow logs. Argo CD reported `oneuptime-homelab` Synced/Healthy, and all four OneUptime pods were Ready.

The Helm repository listed `17.2.0` as its newest chart during this work. OneUptime remains on `10.5.29` per the existing decision to defer its version upgrade.
